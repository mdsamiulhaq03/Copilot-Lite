# MRO application, the standard way: non-RT rApp vs near-RT xApp

## Precision framing (rApp vs xApp — never blur)
- **Non-RT MRO (rApp / classic C-SON)**: control loop **> 1 s** (in practice 15-min/hourly PM ROPs, decisions per hours-days). Inputs are **aggregated PM counters + classified failure events**; outputs are **CM parameter writes** (CIO per relation, hysteresis/TTT per cell). Standardized by 3GPP SA5: LTE = TS 32.522 (SON policy NRM) + TS 32.425 (PM); 5G = TS 28.313 (SON for 5G: MRO function detects too-late/too-early/wrong-cell from UE reports + network info) + TS 28.552 (PM) + TS 28.541 (NRM: `DMROFunction`, `NRCellRelation.cellIndividualOffset`). Commercial reference: AirHop Auptim MRO **rApp** in Ericsson's rApp directory — MRO is commercially a non-RT rApp product category.
- **Near-RT MRO (xApp)**: control loop **10 ms – 1 s** over **E2**. Inputs: E2SM-KPM per-UE/per-cell streams + E2SM-RC report styles (RRC Message Copy, Call Process Outcome, UE Information). Outputs: **E2SM-RC CONTROL Style 3 'Connected Mode Mobility'** (Action: Handover Control per UE with Target Primary Cell ID; also CHO/DAPS actions), optionally INSERT Style 3 (decision interception) or POLICY Style 3. A1 'Traffic Steering Preferences' typed policy (O-RAN.WG2.A1TD) is the standard non-RT→near-RT steering channel.
- A PM-file-driven optimizer over TR-069/NETCONF is a **SON/rApp-style non-RT loop**, not a RIC and not an xApp. CloudlyNet claims must stay on the rApp side of this line (consistent with claims-guardrails.md: no E2, no RIC compliance claims).

## (a) Classic non-RT MRO loop (3GPP SON)
1. **Collect** per 15-min ROP: per-relation HO attempts/successes (LTE `HO.OutAttTarget/OutSuccTarget` on EUtranRelation; NR: `MM.HoExe*` per NRCellCU), classified failures (`HO.OutFail.TooEarly/TooLate/ToWrongCell` per relation in LTE; `HO.IntraSys.TooEarly/TooLate/HandoverToWrongCell` in NR), RRC re-establishment by cause, plus RLF-report-derived context. The classification itself is produced inside the RAN from: UE RLF Report (TS 38.331/36.331 `rlf-Report`: failedPCellId, reestablishmentCellId, connectionFailureType, timeConnFailure, last serving + neighbor measurements), RRC re-establishment causes, and inter-node Xn/X2 **Failure Indication** + **Handover Report** procedures (TS 38.423/36.423). Ping-pong is detected via **UE History Information** time-of-stay, not a raw counter.
2. **Decide** per relation: too-late dominant → trigger earlier (raise CIO toward that neighbor / cut TTT); too-early or ping-pong dominant → trigger later (lower CIO, raise hysteresis/TTT); wrong-cell → adjust the offsets involving the third cell. Respect guardrails: `maximumDeviationHoTrigger*` (±0.5 dB steps in LTE 32.522; -20..20 range in 28.541) and `minimumTimeBetweenHoTriggerChange`.
3. **Actuate** via CM write: `NRCellRelation.cellIndividualOffset` (six SSB/CSI-RS offset components), A3 `a3-Offset`/`hysteresis`/`timeToTrigger` (TS 38.331 5.5.4.4), LTE equivalents per TS 36.331/28.658.
4. **Evaluate** next ROPs against the SON target `hoFailureRate` (TS 32.522) / TS 28.554 mobility KPIs.

## (b) Near-RT xApp variant
- **E2SM-KPM report styles** (v02.01+/v03.00): Style 1 E2-node (cell) measurement; Style 2 single-UE; Style 3 condition-based UE-level; Style 4 common-condition UE-level (the per-UE workhorse); Style 5 multi-UE. Measurements reuse **TS 28.552 names** (DRB.UEThpDl, RRU.Prb*, RRC.ConnMean, MM.Ho*, SS-RSRP distributions). `granularityPeriod` is ms-resolution; practical stacks report 10 ms–1 s (srsRAN supports all 5 styles, capped at 1 s).
- **UE-level RRC events** reach the xApp via E2SM-RC REPORT Style 1 (Message Copy of RRC MeasurementReport), Style 2 (Call Process Outcome), Style 4 (UE Information incl. neighbor L3 info). [Style names/numbers: high confidence for Styles 1-4 semantics; verified via secondary sources, not the raw ASN.1.]
- **Mobility enforcement**: CONTROL Style 3 'Connected Mode Mobility Control' — Handover Control (mandatory params per Rimedo TS xApp spec: UE ID, Primary Cell ID, Target Primary Cell ID, PDU session list, DRB list; optional SCell list), plus CHO and DAPS actions. INSERT Style 3 intercepts gNB-initiated HOs. POLICY Style 3 sets condition-based mobility behaviour.
- **A1 companion**: non-RT rApp computes preferences (analytics/ML) → A1 'Traffic Steering Preferences' policy (SHALL/PREFER/AVOID/FORBID per cellIdList, per UE/slice/QoS-flow scope) → xApp blends policy with live SS-RSRP to pick targets.

## (c) Data volume / latency, and when near-RT is justified
- **Non-RT**: per-cell + per-relation counters at 15-min ROP ≈ a few hundred values/cell/ROP → KB-scale per cell per ROP (MB/day per ~100 cells). Loop latency: one-to-many ROPs (statistical significance needs tens-hundreds of HO events per relation). 3GPP deliberately built MRO as a slow loop — `minimumTimeBetweenHoTriggerChange` is expressed in **minutes** (LTE) / seconds up to 7 days (5G NRM).
- **Near-RT**: per-UE KPM at 100 ms for e.g. 200 UEs × 5 metrics ≈ 10^4 samples/s/cell (plus event-driven RRC message copies) — roughly 4-6 orders of magnitude more data than the PM-file loop, requiring E2 termination, per-UE ID continuity, and sub-second processing. [Estimate, order-of-magnitude.]
- **Near-RT MRO is justified when** decisions are per-UE rather than per-parameter: high-speed users (train/highway/UAV — cell dwell << PM ROP), UE-differentiated steering (QoE/slice/priority), fast-varying load or interference, CHO candidate management, or when acting as MLB+MRO combined per-UE traffic steering (the O-RAN WG3 Traffic Steering use case). **Non-RT suffices** for the classic MRO objective — statistically tuning CIO/hysteresis/TTT — because parameter changes must anyway be evaluated over many HO events; this is why commercial MRO ships predominantly as an rApp (AirHop/Ericsson) and why 3GPP's native loop is PM-driven.

## (e) Minimal viable dataset per variant, and CloudlyNet's gaps
**Non-RT rApp MRO minimum**: (1) per-relation HO attempts+successes; (2) per-relation (or at minimum per-cell) too-early/too-late/wrong-cell classified failures; (3) RRC re-establishment counts by cause; (4) ping-pong signal (time-of-stay or HO-sequence derived); (5) CM read+write of per-relation CIO and per-cell hysteresis/TTT; (6) neighbor relation table + cell identity join keys; (7) guardrail config (max deviation, min change interval). Recommended adds: HO.SrcCellQual/TrgtCellQual, RLF reports, prep-vs-exec split, PRB/RRC load context.
**Near-RT xApp MRO minimum**: (1) E2 interface with KPM (Style 1 + a UE-level style) at ≤1 s granularity; (2) UE-level RRC measurement events (RC Message Copy or equivalent); (3) RC CONTROL Style 3 Handover Control write path; (4) UE ID correlation; (5) A1 (or internal) policy input. Without E2 there is no xApp variant, full stop.
**Gap analysis for a platform with cell-level aggregate HO counters only (no per-relation split, no RLF reports, no E2)** — missing for standard non-RT MRO: `HO.OutAttTarget/OutSuccTarget` (or any per-relation attempt/success), all classified failure counters (`HO.OutFail.*` / `HO.IntraSys.*`), `RRC.ConnReEstabAtt.Cause`-equivalent, UE RLF Report ingestion, Xn/X2 Failure Indication + Handover Report visibility, UE History time-of-stay (ping-pong), `HO.SrcCellQual/TrgtCellQual`, per-relation CIO read/write, A3 hysteresis/TTT read/write, neighbor-relation table, and DMROFunction-style guardrail config. Consequences: (i) with only cell-aggregate attempts/successes you can compute a cell HOSR but **cannot attribute failures to a relation**, so the standard per-relation CIO loop is impossible — only coarse cell-level nudges of hysteresis/TTT remain; (ii) with **no failure classification** the direction of adjustment (earlier vs later triggering) is unknowable from HOSR alone — a low HOSR is compatible with both too-early and too-late regimes; any 'MRO' built on this data is heuristic HO-KPI monitoring, not 3GPP MRO, and must be labeled accordingly; (iii) with no CM write path to CIO/hysteresis/TTT (single-vendor TR-069 EMS device plane) the loop cannot actuate — outputs degrade to recommendations. For the near-RT variant everything is missing (no E2 node, no RIC, no per-UE stream, no RC control). Realistic CloudlyNet path: remain a non-RT, recommendation-first loop; procure per-relation counters and failure classification from the vendor EMS as the single highest-value data ask; use the BDT to synthesize failure labels for RL training in the interim (clearly labeled sim-rung results).
