# RCA incident fixture pack

Contract-exact sample responses for the copilot's RCA loop, over one real incident, so the RCA
agent can be built and tested **before** any MCP tool returns an envelope.

- **Story:** EPIC-8 S9 · **Ticket:** [#367](https://github.com/CloudlyIO/cloudlynet_ai/issues/367)
- **Request record:** [`../HANDOVER-mcp-log-rca.md`](../HANDOVER-mcp-log-rca.md) section 12
- **Contract these validate against:** [`../mcp-envelope.schema.json`](../mcp-envelope.schema.json)
  (v1.1, `cloudlynet.mcp.response.v1`), spec [`../mcp-master-payload.md`](../mcp-master-payload.md)

**These are contract-exact, not byte-exact.** They are hand-built to the frozen envelope, not
generated by the future implementation. Field names, types, invariants and semantics are binding;
the values are the incident.

## The incident

SCTP peer failure -> S1 setup failure -> FM critical `0x16010400` raised -> self-reboot after 90s ->
recovery on cell setup. Verdict: transport outage, autonomous recovery, **not** an actuation
regression. Narrative in
[`../../nanolink/femtocell_dashboard_data_contract.md`](../../nanolink/femtocell_dashboard_data_contract.md)
section 4; envelope walk-through in [`../mcp-master-payload.md`](../mcp-master-payload.md) section 7.

All samples are set at one RCA session, `correlation_id: "rca-8c1f64-2026-06-13"`, run shortly after
the incident, so `timestamp`, `provenance[].as_of` and `freshness_s` are mutually consistent.

## Validate

Every committed sample validates against the envelope schema, formats included:

```bash
python3 -c '
import json, pathlib
from jsonschema import Draft202012Validator as V
s = json.loads(pathlib.Path("artifacts/copilot/mcp-envelope.schema.json").read_text())
v = V(s, format_checker=V.FORMAT_CHECKER); bad = 0
for f in sorted(pathlib.Path("artifacts/copilot/fixtures").rglob("*.json")):
    if f.parent.name == "context": continue
    errs = list(v.iter_errors(json.loads(f.read_text())))
    bad += bool(errs); print(("FAIL " if errs else "ok   ") + str(f))
    for e in errs[:5]: print("      ", list(e.path), e.message[:140])
raise SystemExit(bad)'
```

Run from the repo root. Needs `jsonschema` and `rfc3339-validator`
(`uv pip install jsonschema rfc3339-validator`). Without the format checker the samples still pass;
with it, `date-time` and `uuid` are checked too.

The pack also holds to four invariants the schema cannot express. Worth asserting in your own
adapter tests:

1. `result.count == len(data.items)` on every `collection`.
2. `data.items[*].order_key` is ascending in every collection that has one.
3. Every `page.next_cursor` base64-decodes to `{"boot": ..., "seq": ...}` and names the **first item
   not included** in that reply, so resuming loses nothing.
4. `result.kind: "empty"` implies `count == 0`, `data == {}`, `success: true`, `errors: []`.

## Reading the samples

### The empty-versus-error distinction

`04-empty.json` and `05-error-not-found.json` are the pair to build against first. Both are
"nothing came back", and treating them alike is the failure mode this whole contract exists to
prevent: `empty` means the query was valid and the answer is genuinely nothing, so the agent may
tell the operator the device is quiet. `success: false` means the agent knows nothing at all and
must say so.

### Sizing, with measured numbers

`limit` bounds record count; a server-side size guard may stop earlier. Whichever binds first
governs, and both are always reported. `03-size-cap-truncated.json` is the case where `limit` was
500 and the guard bound instead.

Measured on the same 7 items, compact wire serialisation:

| Shape | Bytes per item |
|---|---|
| Full `device_log_lines` record | ~630 B |
| Lean projection, the 6-field RCA set | ~203 B |
| Ratio | **~3.1x** |

Two caveats worth carrying into your budget math. The payload doc quotes ~700 B full and ~150 B
lean, so about 5x; on this incident the real ratio is **~3.1x**, because alarm lines carry the full
`Alarm Logged, id: … file: … line: … detail: …` grammar and the message text is the part projection
cannot shrink. Lean alarm lines here average ~221 B against ~190 B for non-alarm lines. Size an RCA
window off ~200 B per lean line rather than ~150 B.

### The boot boundary

`get_device_timeline/01-incident.json` and the log samples cross a reboot. Boot B's `seq` restarts
at 0, so its entries are numerically *lower* than boot A's 169 while sorting *after* them under
`order_key`. Anything that sorts, pages or dedups on `seq` or `ts` alone breaks here. This is
deliberately in the pack.

### Alarms are lifecycle records

`get_active_alarms/01-active.json` returns the 31-line ACS backoff series as **one** alarm with
`occurrence_count: 31`. A reply with 31 alarm items would be wrong. `02-cleared-after-recovery.json`
shows the same rows after `ClearingMechanism: CellSetup` fired.

Two of the seven observed alarm ids (`0x02120400` and `0x01110400`) are emitted by the device but
absent from its own `InternalSupportedAlarm` table, so their `clearing_mechanism` and
`recovery_mechanism` are `null` and `catalogue_entry` is `false`. Lifecycle for those ids cannot be
driven from vendor policy. Recorded in
[`context/supported-alarm-catalogue.json`](context/supported-alarm-catalogue.json).

**Corrected 2026-08-14: a collapsed alarm cannot carry an `order_key`.** An `fm_alarms` row with
`occurrence_count: 22` stores one `(boot_epoch, seq)` for a fault seen 22 times, and nothing records
which occurrence that key came from, so pairing the row with a specific log line's `order_key` is a
claim the store cannot back. Earlier revisions of `get_device_timeline/01-incident.json` did exactly
that. Now only `occurrence_count == 1` alarms carry an `order_key` (`0x16010400`, raised and cleared);
the collapsed ones carry `null` and are ordered by `ts` like every other non-line entry. Per-occurrence
keys need per-occurrence lines, which is tranche B.

### `next_actions` are executable

Every `args` object is directly passable to the named tool, unmodified. Where a sample suggests
resuming a page, the cursor in the `args` is the real cursor from that reply. Prose-only
`next_actions` would be a defect.

## Two contract observations from building this

Neither blocks the pack. Both are worth resolving before the tools are implemented.

1. **`mcp-master-payload.md` section 7 is internally inconsistent.** It declares `count: 5` while
   showing 3 items. The fixtures are self-consistent instead (`count == len(items)`), so where they
   differ from the doc's example, follow the fixtures.
2. **`get_device_timeline`'s ordering axis needs a decision.** Section 6.3 says every source exposes
   a comparable `order_key`, but platform-side records (commands, config changes, recommendations)
   have no device `seq`, so no real `order_key` exists for them. Synthesising one from `ts` does
   **not** interleave correctly with device keys, because device keys are prefixed with
   `boot_epoch` rather than the line's own timestamp. These fixtures therefore sort the timeline by
   `ts` ascending (`query.echo.sort: "ts_asc"`) and carry `order_key` where it genuinely exists,
   `null` otherwise. #361 should settle whether that is the contract.

## Provenance and confidentiality

Every value here comes from a **tracked** source. Nothing was read out of `artifacts/real-data/`.

| Source | What came from it |
|---|---|
| `../mcp-master-payload.md` section 7 | seq 163/164/165 in full, boot A epoch, three template hashes, source refs, the tenant uuid, the cursor encoding |
| `../../nanolink/femtocell_dashboard_data_contract.md` sections 2 and 4 | line grammar, the seven alarm ids and their counts, the incident chain and verdict, the archive key scheme |
| `../HANDOVER-mcp-log-rca.md` sections 1, 2, 5, 7, 11 | the query contract, per-line fields, the 24-parameter surface, the FCAPS classes, the v1.1 deltas |
| `../../nanolink/dmcli.new.conf` (tracked) | the 15-entry alarm catalogue, vendor alarm policy, device model and software version, the 24 observed parameter values |
| `submodule/maveric_platform_smo_sim/app/services/nybsys/managed_params.py` | the managed-parameter definitions: types, groups, bounds, writable and optimizable flags |

Anonymisation: the device is `8C1F64-2205609999` everywhere. `8C1F64` is the public vendor OUI and
stays; the serial is the anonymised one. `05-error-not-found.json` uses `8C1F64-9999999999`, the
payload doc's own canonical non-existent device, chosen so it cannot be mistaken for a real serial.

Grep gate, run before finishing and again before any PR:

```bash
grep -rnoE '22056[0-9]{5}' artifacts/copilot/ | grep -v 2205609999 \
  || echo "clean: no serial other than the anonymised 2205609999 appears"
```

The pattern is deliberately written so this file does not itself contain the real serial. It matches
any serial in the device's range and excludes only the anonymised one.

Item 1 (the raw logs) and item 3's real command history are **not here and must not be added**. See
[`context/DELIVERY-item1-item3.md`](context/DELIVERY-item1-item3.md).
