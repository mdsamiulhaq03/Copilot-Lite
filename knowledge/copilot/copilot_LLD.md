# CloudlyNet Copilot - Low-Level Design

**Version:** 0.1.0
**Primary Module:** `submodule/cloudlynet_ai_copilot/backend`

Platform note:
- Platform-side rApp inference now treats ES, LB, and CCO as one shared Non-MRO family. Copilot API routes are unchanged, but any tool/result renderer that surfaces Non-MRO recommendations should expect `tick + items[{cell_id, el_degree, on_off}]`.

## 2. API Endpoints
Base prefix: `/v1/tenants/{tenant_id}/copilot`
Gateway public prefix: `/v1/tenants/{tenant_id}/copilot`
- Gateway forwards `/v1/tenants/{tenant_id}/copilot/**` unchanged to the matching copilot backend route.
- Gateway attaches `X-API-Key` from env `COPILOT_BACKEND_API` on proxied copilot requests.
- Copilot backend mounts tenant-prefixed routes directly under `/v1/tenants/{tenant_id}/copilot/...`.
- Gateway-owned CORS model: backend CORS is disabled by default (`ENABLE_CORS=false`) and can be enabled only for standalone direct use.
- Gateway CORS allow-list is configured by `CORS_ALLOW_ORIGINS` in all environments; release mode requires explicit origins (no localhost fallback).
- Frontend must call gateway routes only; browser calls to `/api/v1/**` are not allowed in platform mode.
- Local Docker note: after gateway proxy/auth changes, rebuild/recreate `gateway` because the compose service runs a compiled Go binary without a source bind-mount. If not, proxied calls can still miss the internal `X-API-Key` headers even when the `.env` values are correct.
- Local platform-admin note: the same local gateway container also owns Cognito-backed `/v1/admin/**` flows, so the gateway local `.env` must carry `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` copied from the deployment Helm gateway `secretData`.

### 2.1 Mandatory frontend request sequence
New chat turn when no active session:
1. `POST /v1/tenants/{tenant_id}/copilot/sessions` with `{query}`
2. take returned `session_id`
3. `POST /v1/tenants/{tenant_id}/copilot/agents/query` with `{session_id, query}`

Follow-up turn in same chat:
1. reuse existing `session_id`
2. `POST /v1/tenants/{tenant_id}/copilot/agents/query`

Important:
- `POST /sessions` creates only the conversation session metadata.
- assistant response is generated by `POST /agents/query`.
- if frontend loses `session_id`, it must recreate/select a session before querying.
- `GET /agents` returns only the user-selectable picker values:
  `debugger_agent`, `data_generation_agent`, `offline_debugging_agent`.
- omit `agent_id` to use backend auto-routing; internal `reactive_agent` and
  `generic_agent` remain implemented and may still appear in stored
  `agent_response.agent_id`.
- deployment-specific frontend origins (local/staging/prod) must be present in gateway `CORS_ALLOW_ORIGINS`.
- when assistant/tool output initiates an async platform action (for example BDT inference), frontend must track the returned run id/Location and poll until terminal status.
- BDT training stability hardening does not add a new frontend route; clients continue to use `/bdt/train` and model polling endpoints.
- The 2026-03-12 Kafka training rollout did not change the copilot contract. Use root `kafka_plan.md` for the platform-side worker/partition implementation status that governs long-running train actions initiated through copilot, including the current `2`-partition / `2`-worker rApp baseline and the quoted-decimal timeout-env fix in deployment values.
- The sibling deployment repo now lets production Kafka/ZooKeeper reuse the shared `efs-pvc` claim already used by rApp/BDT and bootstraps the shared subpaths writable for Confluent's `uid=1000` runtime; this is an infra-only change and does not alter the copilot contract.

## 3. Auth and Identity
Current implementation is demo-mode:
- `app/core/auth.py` returns a static `ClerkUser`.
- `tenant_id` is sourced from the URL path and `user_id` comes from the demo user.
- `app/core/database.py:set_rls_context()` sets PostgreSQL session variables
  `app.current_tenant_id` and `app.current_user_id` for the conversation-table
  RLS policies.

Design implication:
- API endpoints are structured as protected endpoints but still need real token validation and trusted identity propagation in production.

## 4. Data Model
### 4.1 `conversation` schema
- `conversation_session`
  - `id UUID PK`
  - `tenant_id`, `user_id`
  - `title`, `last_message_at`
  - soft-delete fields (`is_deleted`, `deleted_at`)
  - timestamps
- `conversation_message`
  - `id UUID PK`
  - `session_id` FK -> session
  - `current_version_id` FK -> message_version (nullable)
  - `tenant_id`, `user_id`
  - ownership + soft-delete + timestamps
- `conversation_message_version`
  - `id UUID PK`
  - `message_id`, `session_id` FKs
  - `tenant_id`, `user_id`
  - `version_number`
  - `user_query_text`, `agent_id`, `relevant_files`
  - `agent_response`, `edited_agent_response`
  - ownership + soft-delete + timestamps

Legacy upgrade path:
- pre-tenant-isolation databases may still contain `organization_id`
  columns/indexes
- SQL steps in `artifacts/copilot/copilot_prod.md`, and the matching deployment
  chart migration job, backfill `tenant_id` and remove `organization_id`

### 4.2 `knowledge` schema
- `document_source`
  - source registry (`name`, `source_url`, `source_type`, `sync_status`)
- `document`
  - file-level metadata (`file_path`, `content_hash`, `raw_content`)
- `document_chunk`
  - chunk payload + `embedding vector(384)`
  - linked to `document`

Schema reference: `artifacts/copilot/copilot_schemas.sql`.

## 5. Request Lifecycle
### Session creation
1. API validates `query`.
2. `SessionService.create_session()` derives title.
3. Writes `conversation_session` and returns timestamps.
4. Does not create message/response rows.

### Message create
1. API validates payload (`session_id`, `query`, optional `agent_id`).
2. Service verifies session ownership.
3. Inserts `conversation_message`.
4. Fetches history and invokes orchestrator.
5. Inserts `conversation_message_version`.
6. Updates `current_version_id` + session `last_message_at`.
7. Commits transaction.

### Message update
1. Service verifies ownership.
2. Calculates `next version_number`.
3. Re-runs orchestrator with updated query.
4. Inserts new version and updates `current_version_id`.

## 6. Orchestration Details
- Agent selection flow:
  - explicit `agent_id` if provided,
  - otherwise routing agent chooses the best-fit internal or public agent.
- Execution engine: LangGraph state machine.
- Response schema: markdown `content`, `agent_id`, `timestamp`, optional `metadata`.

## 7. RAG Details
- Embeddings: sentence-transformers (`EMBEDDING_MODEL`, default MiniLM).
- Chunking:
  - markdown header-aware,
  - python function/class-aware,
  - token fallback with overlap.
- Search:
  - cosine similarity with pgvector operator `<=>`.
  - threshold and top-k from settings.

## 8. MCP Server

**One server, per-domain tool modules** (EPIC-8). `app/mcp_server/server.py` holds **no** `@mcp.tool`
decorators; every tool is registered by its domain module through `domains/register_all(mcp)`. Domain
separation is code layout, not deployment topology — one process, one port, one registry.

| Module | Domain | Tools |
|---|---|---|
| `domains/data_tools.py` | ingest | 12 |
| `domains/actuation_tools.py` | actuation | 9 (7 read + 2 gated mutations) |
| `domains/observability_tools.py` | observability | 5 registered, plus 2 defined-but-unregistered |
| `domains/optimization_tools.py` | optimization | 5 |
| `domains/ndt_tools.py` | ndt | 3 |
| `domains/policy_tools.py` | policy | 2 (1 conditionally registered) |
| `domains/diagnostics_tools.py` | observability | 1 |

**Registry by flag:** 34 by default → +2 with `MCP_ENABLE_MUTATING_TOOLS` → +1 with the ops DSN *and*
`CLOUDLYIO_ORG_UUID` → 37 with all. The full inventory, the auth model and the frozen one-server
decision live in [`mcp-domain-coverage.md`](mcp-domain-coverage.md).

**Identity** is never a tool argument. `context.py` derives `tenant_id`, `auth_token`, `role`,
`correlation_id` and `request_id` per invocation from the inbound connection; `:8082` decodes the JWT
without verifying it, and the gateway remains the sole enforcement point.

**Every tool returns the `cloudlynet.mcp.response.v1` envelope**, built only through the builders in
`envelope.py`, so `kind: "empty"` with `success: true` (a finding) is never confused with
`success: false` (a failure).

The two placeholder tools that returned hardcoded values (`get_model_accuracy`,
`list_available_models`) were **deleted** in EPIC-8. The offline-debugging agent, whose toolset they
were, now has none and its system prompt no longer advertises them.

Gateway-calling patterns that remain unchanged: `run_bdt_inference` is a call-then-poll
(`POST /v1/tenants/{tenant_id}/bdt/models/{bdt_id}/infer`, then `GET /.../infer/{run_id}`), and
`run_bdt_training` should forward `Idempotency-Key` for safe retrigger under worker redelivery.

Docker entrypoint for SSE mode:
- `app/mcp_server/server_docker.py` (port `8080`, `/health`).


### 8.x Lifecycle tracing (`:8082` container)

Two middlewares plus a boot/shutdown pair, all in `app/mcp_server/trace_middleware.py`, over
stdlib-only primitives in `app/mcp_server/trace.py`. The split keeps `cloudlynet_client` and
`context` — the leaf writers — free of fastmcp and starlette.

| Piece | Hook | Emits |
| --- | --- | --- |
| `boot_report()` | called by the entrypoint before serving | `mcp_boot`: registry size, every tool name, one `gated_off … reason=` per withheld tool |
| `LifecycleTraceMiddleware` | `on_initialize`, `on_list_tools`, `on_call_tool` | `mcp_handshake`, `mcp_list`, `mcp_call` |
| `SessionTraceMiddleware` | ASGI, brackets `GET /sse` | `mcp_session_open`, `mcp_session_close`, `mcp_http_error` |
| `shutdown_report()` | SIGTERM/SIGINT handler | `mcp_shutdown` |

**The `on_call_tool` seam.** Every registered tool returns `str`, so the middleware recovers the
whole envelope from `ToolResult.content[0].text` — all 34 tools, no domain-module edits. It reads
`result`, `errors` and `query` only; **never `data`**.

**`CallTrace`, the accumulator.** A mutable object behind a ContextVar, `trace.begin()` per call,
mutated in place at the leaf. Identity is published by `context.resolve_context()` so the trace
reports what the tool actually used rather than re-decoding the JWT; upstream counts are written by
`cloudlynet_client`. Mutation in place rather than `ContextVar.set()` is required: the timeline
tools fan out through `asyncio.gather`, which copies the context per child task.

**`_request` / `_attempt`.** `_request` counts one logical upstream call; the retried `_attempt`
counts physical attempts, so `up_att > up` is the retry signal. Retries are scoped to idempotent
methods — `httpx.RequestError` cannot distinguish "never sent" from "read timed out after the
gateway acted", and `recommendations/{id}:approve`/`:reject` materialise TR-069 commands.

**Constraints.** Response bodies are never logged at any verbosity. Emission is guarded everywhere
it runs in a `finally`, so a broken trace degrades to no trace rather than to a failed call. The
trace and audit loggers are pinned to INFO independently of `MCP_LOG_LEVEL`; `httpx`, `httpcore` and
`mcp.server.lowlevel.server` are quieted to WARNING, because httpx logs tenant-scoped request URLs.

**Not available in fastmcp 2.14.4:** `on_notification` never fires, and there is no session-teardown
hook — hence the ASGI middleware. See `app/mcp_server/README.md` for the field reference.

## 10. Compose Integration and Isolation
Root compose integration uses shared platform infra resources plus copilot app services:
- shared infra: `postgres`, `redis`, `minio`
- copilot app services: `copilot-backend`, `copilot-mcp-server`
- copilot dedicated DBs on shared postgres: `netai_copilot`, `netai_copilot_test`
- copilot dedicated roles on shared postgres: `netai_copilot_owner`, `netai_copilot_app`
- root `.env` maps those local bootstrap inputs via `COPILOT_POSTGRES_OWNER_*`, `COPILOT_POSTGRES_APP_*`, `COPILOT_POSTGRES_RUNTIME_DB`, and `COPILOT_POSTGRES_TEST_DB`
- existing shared Postgres volumes or cluster DBs must rerun `artifacts/db/init_copilot.sql` before copilot can authenticate successfully
- shared Postgres must expose `pgvector` before copilot knowledge-schema migration can succeed
- schema rollout remains explicit:
  - bootstrap shared Postgres first (`artifacts/db/init_copilot.sql`)
  - apply tenant-upgrade SQL first for older databases (`artifacts/copilot/copilot_prod.md`)
  - apply schema bundle next (`artifacts/copilot/copilot_schemas.sql`)
  - apply conversation-table RLS last (`artifacts/db/init_copilot_rls.sql`)
- local root compose intentionally does not auto-run those schema/RLS steps
- production deployment uses the copilot chart migration job to run those SQL steps in order

## 10A. Kubernetes Deployment Packaging
- Production deployment assets live in `submodule/maveric-deployment`.
- Helm chart: `argocd/maveric_platform_copilot`
  - single chart, two Deployments (`copilot-backend`, `copilot-mcp-server`)
  - rollout order is explicit: SQL migration hook (`sync-wave: 1`), knowledge-base bootstrap hook (`sync-wave: 2`), then backend/MCP Deployments (`sync-wave: 3`)
  - two internal Services (`copilot-backend:8000`, `copilot-mcp-server:8080`)
  - one shared Helm-managed secret (`maveric-aws-copilot`) carrying backend and MCP env keys
  - one chart-packaged knowledge-base archive (`files/knowledge_base.tgz`) rendered through `templates/knowledge-base-configmap.yaml`
  - one chart hook job (`templates/knowledge-base-job.yaml`) that expands the archive into an `emptyDir`, runs `uv run python scripts/ingest_knowledge_base.py`, then runs `uv run python scripts/contextualize_chunks.py --skip-existing`
  - consumes existing cluster Postgres, Redis, and object-storage endpoints from values-driven secret data
  - backend service name source of truth: `templates/backend-service.yaml` + `templates/_helpers.tpl` (`maveric_platform_copilot.backendFullname`)
  - `CLOUDLYNET_API_KEY` stays an optional blank env until a dedicated secret is provided.
    `MCP_CLOUDLYNET_API_KEY` is gone (EPIC-8): the MCP server forwards the caller's bearer instead
- Jenkins pipeline: `jenkins/maveric_platform_copilot.groovy`
  - builds backend image from `backend/Dockerfile`
  - builds MCP image from `backend/app/mcp_server/Dockerfile`
  - updates both image tags together in the single Helm chart values file

Isolation controls:
- copilot data isolation is database/schema-level, not infra-container-level.
- copilot backend and MCP server run on shared `maveric` network in compose.
- root compose remains the single infra source of truth.
- copilot readiness probes should prefer `/v1/tenants/{tenant_id}/copilot/health`; the legacy direct alias `/api/v1/health` remains available for compose/container probes, while `/health` stays the lightweight process check.
